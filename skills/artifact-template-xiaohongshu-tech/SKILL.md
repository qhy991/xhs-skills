# 小红书科技图文制作

把用户的观点做成一套可读、可信、可直接选图发布的小红书图文。完成文案、成图、检查和下载包；不要只交大纲、提示词、HTML 或一张长拼图。按用户当前明确要求覆盖默认值。

## 先读这些资源

- 开始写作时读 [叙事与文案](references/editorial-playbook.md)。
- 开始设计时读 [视觉规范](references/visual-system.md)，并查看 `assets/reference.png`：这是已完成的苹果 GPU 九图总览，只作结构和视觉参考。
- 使用渲染器前读 [配置与运行方法](references/renderer-schema.md)，从 `assets/example-post.json` 复制工作配置。
- 排查制作或交付问题时读 [制作与交付](references/production.md)。
- 需要细看时查看 `assets/reference-cover.png` 和 `assets/reference-content.png`。保留这些原始参考图，不覆盖它们。

把所有路径按本技能所在目录解析。在新的工作目录写当次文案、配置、素材和成品，不向技能目录写发布产物。不要把参考图中的公司、产品、日期或趋势沿用到新选题。

## 默认成品

| 项目 | 默认值 |
| --- | --- |
| 读者与语气 | 对科技、AI、编程与个人成长有兴趣的读者；第一人称、有判断、能解释 |
| 图数 | 9 张；信息较少时减至 6–8 张，用户给定页数时优先遵守 |
| 画布 | 1440 × 1920 px，3:4 竖版，逐页独立文件 |
| 风格 | 深绿、米白、荧光绿；大标题、清晰留白、卡片与简洁图解 |
| 制作 | 封面无字插画用 imagegen；准确文字、卡片、图标与关系图用 Node Canvas |
| 交付 | 编号 JPG、无损 PNG、完整总览、标题与正文、来源清单、发布说明和 ZIP |

这些是制作默认值，不是平台官方上传限制。不要宣称已经替用户发布。

## 1. 确定内容承诺

从当前对话提取主题、核心观点、读者、想让读者采取的行动，以及可使用的素材。信息足够时直接做，不为字体、配色、页数等常规选择反复追问。把内容承诺写成一句话，例如“解释我为什么看好这个方向，并给出今天就能开始的第一步”。

保留用户原有立场，但把空泛的“红利”“风口”“必争之地”改成具体的需求、工程问题、学习成果或行动。可以推荐，也要给出推荐的理由。

若用户只要求文案或分析，按所要求的范围交付；若要求可发布图片，完成后续全部阶段。

## 2. 核查能影响结论的事实

先核对公司、产品、项目、模型和工具名称。对近期发布、能力、价格、性能、兼容条件与就业信息检索当前资料，技术事实优先使用官方文档、模型卡、项目仓库、发布博客或论文。

工作中维护“主张 → 来源 URL → 日期 → 使用条件 → 可写表述”清单。明确区分事实、用户个人经历、作者判断与预测。不编造自己的实测、从业经历、收益或招聘增长。没有确认的专名不要猜着放进成图；删除次要例子或向用户询问会改变核心判断的缺口。

核对推理链条，尤其注意：能在电脑上操作不等于模型在本地推理；硬件中相邻的加速单元不等于同一种编程接口；设备总量不等于满足某模型配置的设备量；单个 benchmark 不等于所有任务更快。仅在对应选题适用时使用这些检查。

图上放简短来源名称和影响结论的必要条件；完整 URL、核查日期及限制写入 `sources.txt`。事实与预测可以相邻，但用“我的判断”“我更看好”等自然措辞标清。

## 3. 先写整套文案，再做图片

默认按以下叙事推进，允许合并或替换槽位：

1. **封面**：明确观点或问题，突出主题，给出继续看的理由。
2. **变化信号**：用一两个已核查的例子说明发生了什么。
3. **用户需求**：让读者看到它与日常工作的联系。
4. **体验或问题**：拆成响应、成本、效率等三个具体维度。
5. **平台或方案条件**：解释为什么选择这个方向，给简洁图解。
6. **为什么是现在**：连接需求、工具、场景，标清作者判断。
7. **能做什么**：给一个工程闭环或三步方法。
8. **个人收益**：落到作品、能力、开源贡献等可验证成果。
9. **开始行动**：给三四步起点，以一句具体行动结束。

每页只承担一个主要结论。用短标题、少量支撑句和一个收束句；不要把长文章硬塞进卡片。先减少文字，再考虑增加页面；禁止为塞下内容静默缩小正文。

同时写 `caption.txt`：推荐发布标题、约 400–700 字正文、3–6 个相关标签。该字数是编辑默认值，允许按内容与用户要求调整。正文补足理由与行动，不机械抄录每张图。无需给用户大量备选让其自己拼装。

## 4. 制作素材与排版

默认采用本次作品的混合制作方法：

- 用当前可用的 imagegen 能力生成与主题匹配的无文字封面插画。先读其技能和工具说明；按视觉规范的 hero 提示词替换主体。不要用代码绘画冒充 AI 插画，也不要把旧主题设备图无条件放到新主题。
- 使用 `scripts/render_carousel.cjs` 以 Canvas 排准确的中文、卡片、页码、图标和关系。原方法是 Canvas 直接导出图片，**不是 HTML 截图，也不是整页 AI 生成**。
- 对数据图、技术关系和数值用确定性绘制，保留清楚的标注；不让 imagegen 决定精确结构或生成数据。
- 若用户明确要求全部用 imagegen，逐页生成并逐页核对文字和事实，按图像能力要求修订；不要继续用默认 Canvas 流程而声称全部生成。若用户明确要求 HTML，可用固定画布 HTML/CSS 导出同规格图片，并准确描述实际方法。
- 不可调用 imagegen 时，继续完成文案和布局，把能力限制说明清楚；只有用户已允许无插画版或明确选择程序示意时才以该版本交付。示例配置的程序示意封面仅用于验证渲染器。

使用支持简体中文的字体文件，显式传入常规体和粗体。缺失字体应先找到可用中文字体，禁止带着方框字、字体回退或假粗体交付。字体与依赖不使用过去会话的绝对路径。

## 5. 渲染与检查

把当次内容填入新的 JSON 配置，使用一个新的输出目录，按 `references/renderer-schema.md` 运行渲染器。生成所有独立图和总览。

在交付前完成以下检查：

- 阅读每张图的全部文字，核对错字、专名、数字、来源与事实条件。
- 查看九宫格总览，检查明暗节奏、标题层级、风格与叙事是否连贯。
- 查看每张全尺寸图或按页放大，检查截断、重叠、错误连线、乱码、留白与边距。
- 查看约 360–430 px 宽的阅读效果；正文应易读，关键条件不能只藏在小脚注。
- 检查 `layout_audit.json` 无越界，页数和文件顺序一致；自动审计不能代替视觉检查。

发现问题后改文案或布局，重渲染受影响页面，再检查该页与总览。不为低风险排版写一套冗余测试。用户未要求时不展示调试日志。

## 6. 打包到可发布的状态

使用 `scripts/pack_publish.py` 校验并打包。将正文和来源先保存成 UTF-8 文本。程序检查图片数、编号、1440 × 1920 尺寸、配套 JPG/PNG、渲染审计和 ZIP 完整性。

发布包必须包含：

```text
01_ready_to_post_JPG/01_…jpg → 按编号选择并上传
02_lossless_PNG/01_…png     → 无损备份
03_copy_and_sources/caption.txt
03_copy_and_sources/sources.txt
03_copy_and_sources/readme.txt
03_copy_and_sources/overview.png
```

不把缓存、调试图、测试产物、字体、依赖、旧版本、个人文件或鉴权信息放入发布包。需保留可编辑源码时另存，不混入选图文件夹。

按照当前环境的文件保存规则保存成品；需要时使用 Library 能力。用户要求的是可下载图片时，提供真实可下载的 ZIP 和总览，不能只给源代码或提示词。上传、发布到小红书需要用户另行明确授权。

## 7. 交付时说清楚

首句说明完成了多少张、尺寸与风格。给出发布 ZIP 的可点击链接、总览预览和一个推荐标题；说明“解压后按 01 到末页顺序选择 JPG，正文见 caption.txt”。只说明实际存在的文件和已完成的检查。

对重要修正用一两句说明其对结论的影响。用户问制作方式时如实解释 AI 插画与程序排版的分工，不把混合制作称为整页 AI 生图。

# 科技学习图文：内容编排手册

把一项科技、AI 或工程学习主题，写成用户愿意以第一人称发布的图文：有明确判断，有能核对的依据，有一个可以开始的行动。先完成内容卡，再进入视觉排版；不要把长文直接截图成九页。

## 1. 先锁定一句主张

用现有上下文确定四件事：推荐谁学、推荐学什么、为什么现在、学完能做什么。信息足够时直接采用合理默认，不为常规风格或页数反复确认。

将主张写成一句可检验的判断，例如：“我推荐有编程基础的开发者现在学习某项技术，因为新需求、可用工具和真实项目正在汇合。”正文保留“我推荐”“我看好”“我的判断”，但不编造用户亲测、工作经历、成绩或立场。

稿件标题按约 18–22 字做设计默认，例如“为什么我推荐现在学某项技术”。这是标题设计长度，不是平台发布限额；用户指定标题优先。封面可以拆为 2–3 行，每行控制在 6–10 个汉字左右；英文按实际渲染宽度判断。

## 2. 用九个叙事槽位组织内容

默认 9 页。主题材料较少时收缩到 6–8 页：合并相邻的“场景与需求”“条件与时机”“工作与收益”，保留开头主张、事实依据和结尾行动。不要为凑页重复同一理由。

| 页 | 叙事任务 | 放什么 | 建议结构 |
|---|---|---|---|
| 01 主张 | 告诉读者为什么值得继续看 | 用户第一人称推荐、主题、目标收益 | 三行封面标题＋一句副标题＋2–3 个主题标签 |
| 02 信号 | 给判断一个事实起点 | 1–2 个已核实的发布、工程或研究案例 | 两张证据卡；每个案例只解释它证明什么 |
| 03 场景 | 让读者看到真实需求 | 谁在什么任务中会用到这项技术 | 3–4 个具体场景，围绕一个共同需求 |
| 04 要求 | 把需求接到技术问题 | 速度、质量、资源、成本、稳定性等真正相关指标 | 3 个指标或能力卡；写清用户感受 |
| 05 条件 | 说明为什么关注这个平台或方法 | 2–3 个技术条件及其用途 | 一个核心机制示意＋两张补充卡 |
| 06 时机 | 回答为什么现在开始 | 能力、工具、应用场景的近期变化 | 3 条成熟信号，标明资料日期 |
| 07 工作 | 解释学习者可以具体做什么 | 诊断、实现、验证，或该领域等价工程过程 | 三步流程；每步有动作与可观察结果 |
| 08 收益 | 把学习机会落到作品 | 分析报告、实现、开源贡献、可用产品等 | 3–4 张作品卡；说明能证明什么能力 |
| 09 行动 | 降低开始成本 | 一个小项目的 3–4 步路径 | 编号步骤＋一个完成标准＋一句收束 |

迁移主题时替换槽位内容，不保留苹果、模型或就业等特定论点。每个槽位都必须服务本次主张；某一槽位不成立就合并或换成实际需要的问题。

## 3. 先写“内容卡”，再压缩到图中

每页内容卡固定记录：页码、叙事任务、大标题、短副标题、2–4 个内容单元、一句重点、事实来源、必要限定。重点句推进本页结论，不复述标题。

| 元素 | 默认容量 |
|---|---|
| 内页大标题 | 8–16 个汉字左右，1–2 行 |
| 副标题 | 15–30 字，1 行优先 |
| 内页正文 | 约 60–130 个中文字符；复杂内容先拆页或删减 |
| 单张卡片 | 一个小标题＋1–2 句短说明；不要放整段论文式文字 |
| 重点句 | 12–24 字，通常一行，最多两行 |
| 图内来源与限定 | 最多两行，完整 URL 留在来源文本 |
| 封面 | 大标题、一个观点副标题、一个主视觉；正文比内页更少 |

这些是写作预算，最终以实际字号、文字测宽和手机预览为准。先删重复观点、次要背景和术语解释，再考虑缩字。不要把正文缩到脚注大小来塞满卡片。

使用短句和具体动词。介绍一个项目后马上说明它与主张的关系。技术名词只保留识别对象或理解因果所需的部分。避免公司履历、融资故事、多个排行榜和无关参数抢走主线。

## 4. 为关键事实建立小型证据表

在排版前，为每个关键事实记录“原句／来源 URL／发布日期或版本／适用条件／事实还是判断”。近期发布、功能、产品名、性能、硬件支持、岗位和价格都重新核实。优先打开官方发布、官方文档、代码仓库、模型卡或原始论文；搜索摘要只用于找来源。

先核对人名、公司名、产品名和代码项目名，纠正口述或拼写错误。不要根据近似名称补出不存在的产品。分清发布时点、网页更新时间与检索日期。

事实使用明确陈述；趋势推断使用“我判断”“我看好”“这给了……机会”。一两个案例可以证明存在某种做法，不能直接证明整个行业已经转向它。性能数字必须连同设备、版本、输入条件、精度或量化、测量口径一起保留；图文无需数字时，优先讲机制。

通用校准反例：

- “Agent 能操作本机”不等于“模型在本机推理”；产品案例要放在它实际支持的论证层。
- 名称相近的处理单元不等于同一硬件。例如 GPU 内神经加速器与独立 NPU/ANE，需要按本次平台资料区分。
- “能运行某模型”不等于所有设备都能获得同样体验；内存、上下文、精度与软硬件版本可能改变结论。
- “出现公开岗位”可以证明某类需求存在，不能推出岗位即将爆发、学会即就业或收入保证。
- 本地、低功耗、隐私与安全分别对应不同机制，不把其中一个优势当作其余优势的证明。

这些是核查方法的反例，不是永久固定的产品事实。每次以最新一手来源和本次任务边界为准。

## 5. 写发布配文与来源

配文写成完整的第一人称短文，中文主体约 400–700 个中文字符；标题和标签另列。英语产品名保留正确写法，不为了字数删掉必要条件。建议顺序：

1. 一句个人判断。
2. 一两个关键事实及它们带来的变化。
3. 对读者有什么意义。
4. 一条现实的开始路径。

配文补充图片之间的逻辑，不逐页重复九个标题。选 3–6 个真实相关的标签，覆盖主题、技术和读者方向；不添加无关热点或流量承诺。

来源文本列出核对日期、来源名称、完整 URL 和它支持的内容。来源只引用实际查阅并支持成稿的材料。图内使用简短来源名；不要把检索工具标记、超长 URL 或聊天引用语法直接绘入图片。

## 6. 内容交付前只查关键问题

- 读完封面和全部重点句，是否能复述主张及理由？
- 事实、作者判断和行动建议是否清楚？有没有替用户编造体验？
- 每页是否只推进一个主要观点？前一页是否为后一页提供理由？
- 技术边界是否放在真正需要的位置，且没有变成长篇免责说明？
- 结尾的小项目是否有可完成的第一步和可观察的结果？
- 图片、配文和来源的名称、数字、日期是否一致？

交付直接可发布的图片、完整配文和来源文件。用户要求“可以发布”表示准备好发布素材；只有明确要求发布时，才进入外部发布流程。
